\section{Erweiterung der Ausgangslage}
\subsection{IST-Stand}
\label{sec:ist-zustand}
Benutzer, die sich über die EcoHub-Plattform bei Pax anmelden möchten, müssen aktuell initial manuell über eine interne Eingabemaske im LDAP-Verzeichnis angelegt werden. Dabei wird zwischen Private Vorsorge (PV) und Berufliche Vorsorge (BV) unterschieden. Ein Broker, der durch diese Maske im LDAP erfasst wird, erhält anschliessend die notwendigen Rollen und Gruppen.

Dieser Prozess erfolgt manuell, ist fehleranfällig und verursacht hohen administrativen Aufwand.

Sollte sich ein Broker anmelden wollen, der nicht im LDAP vorhanden ist, scheitert der Vorgang, da aktuell keine automatische Benutzererstellung existiert. Die vorhandene \texttt{addUser}-Funktion generiert eine IDP-Nummer, welche für die Durchführung des Single Sign-On (SSO) zwingend erforderlich ist. Die Web Access Management (WAM) prüft im Rahmen des SSO auf das Vorhandensein dieser IDP-Nummer. Fehlt sie, wird der Zugriff verweigert.

Auf der EcoHub-Plattform existieren bereits eigene Berechtigungskonzepte. Diese stimmen grösstenteils mit jenen der Pax überein. Es wird zwischen Einzelleben (EL) und Kollektivleben (KL) unterschieden (siehe Abbildung \ref{fig:rollenEcoHub}). Obwohl diese Rollen über EcoHub zugewiesen werden können, werden sie derzeit nicht automatisch in das LDAP-Verzeichnis übernommen und operativ nicht weiterverwendet

\subsection{LDAP-Verzeichnisstruktur}
\label{sec:ldap-struktur}

Zur besseren Nachvollziehbarkeit der bestehenden Benutzerverwaltung wurde im Rahmen der Analysephase auch die aktuelle LDAP-Struktur untersucht. Abbildung~\ref{fig:ldap-struktur} zeigt den lokalen Aufbau des LDAP-Verzeichnisses im Projektkontext.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\textwidth]{images/LDAP_Struktur_lokal.png} 
    \caption{LDAP-Verzeichnisstruktur im lokalen Setup (Quelle: Eigene Darstellung)}
    \label{fig:ldap-struktur}
\end{figure}

Die Struktur gliedert sich wie folgt:

\begin{itemize}
    \item \textbf{Basis-Domain:} \texttt{dc=paxportal,dc=ch}
    \item \textbf{Organisatorische Einheiten (OUs):}
    \begin{itemize}
        \item \texttt{ou=groups}: Enthält LDAP-Gruppen, welche externen Rollen zugewiesen sind. Die Gruppen folgen dem Namensschema \texttt{cn=EXTERNPAX\_A\_<ROLLE>} und bilden verschiedene Anwendungen wie \texttt{BROKERPORTAL}, \texttt{LOGISMATA\_B2B} oder \texttt{QUICKSALE} ab.
        \item \texttt{ou=people}: Beinhaltet Benutzerobjekte, unterteilt in:
        \begin{itemize}
            \item \texttt{ou=Makler}: für Broker-Nutzer
            \item \texttt{ou=Mitarbeiter\_AD}: für interne AD-Mitarbeitende
            \item \texttt{ou=Mitarbeiter\_GS}: für weitere interne Mitarbeitende
        \end{itemize}
    \end{itemize}
\end{itemize}

Die im Bild gezeigten Benutzereinträge (\texttt{uid=laura.schmidt}, \texttt{uid=hans.muster} etc.) sind \textbf{ausschliesslich Dummy-Daten} und dienen lediglich der Veranschaulichung.

\subsubsection*{Relevanz für das Projekt}

Diese LDAP-Struktur ist zentral für den \textit{EcoHub Provisioning Service}, welcher Benutzer automatisiert erstellt, aktualisiert oder löscht. Dabei ist besonders die rollenbasierte Gruppenzuweisung entscheidend: Über ein externes Mapping (z.\,B. \texttt{EL\_}, \texttt{KL\_}) wird gesteuert, in welche Gruppen ein Benutzer aufgenommen wird.

\subsubsection*{Datenschutz und Veröffentlichung}

Vor der Integration dieser Struktur in das GitHub-Repository wurde geprüft, ob die \texttt{cn}-Bezeichner der Gruppen bedenkenlos veröffentlicht werden dürfen. Diese Klärung war notwendig, um sicherzustellen, dass keine vertraulichen oder geschützten Produktionsinformationen offengelegt werden. Die hier gezeigte Struktur ist vollständig anonymisiert und enthält keine personenbezogenen oder produktiven Daten.

Die meisten Endpunkte besitzen eine eigene XML-Struktur, welche den jeweiligen Verwendungszweck widerspiegelt. Die Struktur ist vorgegeben, wurde aber im Rahmen der Analyse hinsichtlich Relevanz und Vollständigkeit geprüft.

\subsection{Analyse der bestehenden CI/CD-Pipeline}

Zur Qualitätssicherung und Automatisierung der Build- und Testprozesse wird im Projekt eine GitHub-Actions-basierte CI/CD-Pipeline eingesetzt. Diese ist in der Datei \texttt{pipeline.yml} definiert und wird bei jedem \texttt{push} ins Repository ausgeführt.

\subsubsection*{Übersicht der Jobs}

Die Pipeline besteht aus vier zentralen Jobs:

\begin{itemize}
  \item \textbf{test:} Führt automatisierte Unit-Tests mit Maven aus
  \item \textbf{build:} Erstellt das Projekt und bereitet ein Docker-Image vor
  \item \textbf{publish:} Veröffentlicht das Docker-Image in eine Container Registry (nur bei Tags)
  \item \textbf{delete\_artifacts:} Entfernt erstellte Artefakte nach erfolgreicher Veröffentlichung
\end{itemize}

\subsubsection*{Technische Details (Auszug Job \texttt{test})}

\begin{lstlisting}[language=yaml, caption={Auszug aus pipeline.yml}]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '17'
      - name: Execute tests
        run: chmod +x ./mvnw && ./mvnw test
\end{lstlisting}

Die Tests werden vor dem Build ausgeführt und dienen als Quality-Gate. Nur bei erfolgreichem Testdurchlauf wird das Projekt gebaut und ein Docker-Image erzeugt.

\subsubsection*{Integration in den Entwicklungsprozess}

Diese Pipeline bildet die Grundlage für die kontinuierliche Validierung und Bereitstellung des Provisioning-Dienstes. Dadurch wird sichergestellt, dass:

\begin{itemize}
  \item Änderungen stets mit bestehenden Funktionalitäten kompatibel sind
  \item Fehler frühzeitig erkannt werden
  \item Releases nur bei validierten Git-Tags veröffentlicht werden
\end{itemize}

Die wichtigsten Container im aktuellen System sind:

\begin{itemize}
    \item \textbf{Web Application Firewall (WAF):}  
    Führt IP-Whitelisting sowie Zertifikatsprüfungen durch und schützt die Schnittstellen gegenüber dem Internet.
    
    \item \textbf{API-Management:}  
    Verwaltet eingehende API-Anfragen, prüft auf Richtlinien (Policies) und leitet validierte Anfragen an die zuständigen Systeme weiter.
    
    \item \textbf{Web Access Management (WAM):}  
    Übernimmt die zentrale Authentifizierung (SSO) und prüft anhand der IDP-Nummer im LDAP, ob ein Benutzer autorisiert ist.
    
    \item \textbf{OpenLDAP:}  
    Verzeichnisdienst zur Speicherung von Benutzerdaten, insbesondere E-Mail-Adressen und IDP-Nummern.
    
    \item \textbf{EcoHub Provisioning Service:}  
    Eine Spring Boot-Anwendung, bereitgestellt auf Azure Kubernetes (AKS), welche Benutzer über SOAP-Schnittstellen verwalten kann (hinzufügen, aktualisieren, löschen).
    
    \item \textbf{PAX Portal:}  
    Die Zielplattform, auf die Broker nach erfolgreichem Login weitergeleitet werden, wenn alle Prüfungen bestanden wurden.
\end{itemize}

Die Kommunikation zwischen diesen Containern erfolgt aktuell sequenziell, mit mehreren Prüfungen und Sicherheitsbarrieren. Änderungen oder Fehler in einem der Container können sich direkt auf das Verhalten des Gesamtsystems auswirken.

Er stellt eine SOAP-Schnittstelle zur Verwaltung von Broker-Benutzern bereit. Die Benutzerverwaltung erfolgt durch Interaktion mit einem extern angebundenen OpenLDAP-Verzeichnisdienst.

\vspace{1em}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{images/System-EcoHub_C3.png}
    \caption{C3-Komponentendiagramm - EcoHub Provisioning Service (Quelle: Eigene Darstellung)}
    \label{fig:c3diagramm}
\end{figure}

Die wichtigsten Komponenten im Diagramm sind:

\begin{itemize}
    \item \textbf{UserProvisioningEndpoint} \\
    SOAP-Webservice-Endpunkt, der externe Anfragen wie \texttt{addUser}, \texttt{updateUser}, \texttt{deleteUser} oder \texttt{getUserStatus} entgegennimmt.

    \item \textbf{UserProvisioningService} \\
    Zentrale Geschäftslogik. Validiert die Anfragen, delegiert LDAP-Operationen und erstellt Rückgabemeldungen.

    \item \textbf{ValidationService} \\
    Führt strukturierte Prüfungen der eingehenden Payloads durch (z.\,B. Pflichtfelder, Formate, Längenbeschränkungen) und verwendet Adapter-Objekte zur Entkopplung vom SOAP-Modell.

    \item \textbf{ResponseCreatorService} \\
    Baut standardisierte Antwortobjekte (inkl. Fehlermeldungen) zur Rückgabe über SOAP.

    \item \textbf{PersonRepository \& PersonRepositoryImpl} \\
    Repositories zur Suche, Änderung und Löschung von Nutzerdaten im OpenLDAP-Verzeichnis. Nutzen \texttt{LdapTemplate} von Spring.

    \item \textbf{OpenLDAP (extern)} \\
    Verzeichnisdienst, der Brokerdaten und ihre Rollen speichert. Wird durch den Provisioning Service gelesen und beschrieben.

    \item \textbf{EcoHub (extern)} \\
    Die EcoHub-Plattform ruft den Provisioning-Service über eine definierte WSDL-Schnittstelle auf und sendet XML-basierte Requests.
\end{itemize}

Die Kommunikation erfolgt synchron via SOAP, die Daten werden direkt im LDAP-Verzeichnis persistiert. Alle Komponenten sind lose gekoppelt und durch Interfaces und Adapter abstrahiert, was Testbarkeit und Erweiterbarkeit verbessert.


\subsection{Problemanalyse}
\label{sec:problemanalyse}
Schwachstellen sind konkrete Mängel oder Probleme im aktuellen System oder Prozess. Sie beschreiben, was heute nicht gut funktioniert und somit den Änderungsbedarf begründet. Darunter fallen aktuell folgende Punkte:

\begin{itemize}
    \item Der Benutzer muss manuell im LDAP eingetragen werden, was ein hoher Aufwand ist und die manuelle Bearbeitung birgt ein hohes Fehlerrisiko.
    \item Die Rollen von EcoHub werden nicht im LDAP übernommen, was bedeuten kann, dass Broker im EcoHub andere Berechtigungen haben.
    \item Es gibt keine Tests auf die Endpunkte des EcoHub-Services. Schlägt ein Endpunkt fehl oder werden Änderungen gemacht, wird der Nutzer es als erstes bemerken.
\end{itemize}



\subsection{Chancen und Risiken}
\label{sec:chancen-risiken}
Risiken sind mögliche Probleme oder Gefahren, die beim Projektverlauf oder der Umsetzung der Änderung auftreten könnten - also zukünftige Unsicherheiten. Folgende wurden für dieses Projekt erkannt.

\begin{itemize}
    \item Fehlerhafte Zuordnung von Rollen. Die Mapping-Funktion weist den Broker in falsche Gruppen und Rollen.
    \item Änderung an LDAP-Struktur. Ungründliche Vorbereitung und Arbeiten könnte die LDAP-Struktur verändern.
    \item Unvollständige Testabdeckung. Werden die Funktionen oder Endpunkte nicht vollständig abgedeckt, kann es weiterhin zu unentdeckten Problemen führen.
\end{itemize}


\subsection{ Zielsetzung}
Nun sind verschiedene Ziele für das EcoHub vorgesehen. Der ganze Prozess soll automatisiert geschehen, das bedeutet die manuelle Erstellung der Broker über die Maske fällt weg. 
Der Broker soll die Möglichkeit bekommen, über das EcoHub sich bei der Pax anzumelden, insofern er eine Service-Vereinbarung eingegangen ist, und damit ein neuer Nutzer im LDAP erstellt und gespeichert wird. 
Bei der Erstellung wie aber auch nachträglich sollen die Berechtigungen, die der Broker auf der EcoHub-Plattform erhält, die gleichen sein wie die im LDAP. 
Auch die einzelnen Schnittstellen des EcoHub-Services sollen getestet werden, um Probleme vorzeitig zu erkennen und zu lösen.

\subsection{ Abgrenzung}
\label{sec:abgrenzung}
Wichtig ist, sich nicht in der eigenen Arbeit zu verlieren oder sich in andere Aufgaben zu verlieren. Die Automatisierung des Prozesses, um einen neuen Broker hinzuzufügen, ist nicht Teil der IPA.
Auch dass die Gruppen-Zuteilung bei der initialen Anmeldung geschieht, ist nicht Teil der IPA.

\section{Erweiterte Aufgabenstellung}
Die Aufgabe in dieser IPA bezieht sich auf zwei der Ziele. Es soll eine Mapping-Funktion geschrieben werden welche die EcoHub Rollen mit den internen Rollen verbindet. Das soll geschehen sollten sich die Rollen des Broker ändern und ein update nötig sein.
Auch sollen alle Schnittstellen des EcoHub-Services automatisiert getestet werden, die Automation soll über eine Pipeline laufen.


\section{Anforderungen}
\subsection{Funktionale Anforderungen}
Bei Funktionalen Anforderungen handelt es sich um das (WAS?). Was soll das System oder Produkt tun, besser gesagt welche Funktionen oder Verhaltensweisen muss es bieten. Folgend die wichtigsten Funktionalen Anforderung im bezug auf die zwei Aufträge.
\subsubsection{Mapping-Funktion}
\begin{itemize}
    \item Der Broker wird entsprechend seiner EcoHub-Rolle den korrekten Gruppen im LDAP zugeordnet.
    \item Gruppen, in denen der Broker nicht mehr Bestandteil ist, aus denen wird er entfernt.
    \item Bei nicht bekannten Rollen wird die Anfrage ignoriert und der Broker kriegt keine neuen Berechtigungen.
    \item Die Funktion muss das Mapping aus einer externen Konfigurationsdatei (z.B. application.yml) laden, damit Änderungen ohne Codeanpassung möglich sind.
    \item Die Funktion muss mehrere Rollen gleichzeitig verarbeiten können.
\end{itemize}
\subsubsection{API-Testautomatisierung}
\begin{itemize}
    \item Alle bekannten API-Endpunkte des EcoHub-Provisioning-Services müssen durch automatisierte Tests abgedeckt werden. 
    \item Die Tests müssen sicherstellen das konkrete Fehlermeldungen zurückgegeben werden.
    \item Tests müssen jederzeit wiederholbar sein, ohne manuelle Vorbereitung (z.B. Setup- und Teardown-Routinen für Testdaten).
    \item Die Tests müssen nicht nur wiederholbar sondern auch automatisch durchgeführt werden. 
\end{itemize}

\subsection{Nicht-funktionale Anforderungen}
Bei nicht-funktionalen Anforderungen handelt es sich um das (WIE?). Wie soll das System funktionieren und welche Qualität soll dieses bieten.
\subsubsection{Mapping-Funktion}
\begin{itemize}
    \item Die Verarbeitung einer Mapping-Anfrage soll maximal 500 ms dauern.
    \item Ungültige oder unbekannte Rollen verursachen einen kontrollierten Fehler mit Logging.
    \item Die Mapping-Logik muss durch Unit-Tests abdeckbar sein.
\end{itemize}
\subsubsection{API-Testautomatisierung}
\begin{itemize}
    \item Die komplette Testausführung soll in unter 2 Minuten durchführbar sein, um schnelle Feedback-Zyklen zu ermöglichen.
    \item Für die Tests dürfen keine sensitiven Daten verwendet werden. Es werden Testdaten genutzt, welche nicht mit echten Nutzern in Verbindung gebracht werden können.
    \item Die Testfälle müssen gut strukturiert, benannt und dokumentiert sein, sodass sie auch von Dritten gepflegt werden können.
    \item Das Testsystem soll erweiterbar sein, damit neue Endpunkte mit geringem Aufwand integriert werden können.
\end{itemize}

\section{Rahmenbedingungen und Annahmen}
Rahmenbedingungen beschreiben äussere Faktoren und definieren den Spielraum, der das Projekt nicht aktiv beeinflusst, an den sich aber gehalten werden muss. Für diese Arbeit gelten folgende Rahmenbedingungen:

\begin{enumerate}
    \item Das bestehende LDAP-System (OpenLDAP) darf nicht strukturell verändert werden (Schema, Gruppenstruktur bleibt gleich).
    \item Es muss eine bestehende Spring Boot Applikation verwendet werden.
    \item Es dürfen nur bereits vorhandene Gruppen im LDAP verwendet werden.
    \item Die Integration erfolgt via SOAP-Schnittstelle des EcoHub.
    \item Die API-Tests werden mit Playwright gemacht, da Pax weit alle API- und End-to-End-Tests mit Playwright geschrieben werden.
\end{enumerate}
